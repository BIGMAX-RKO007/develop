# Presto

## 背景

FaceBook觉得Hive不够用了，性能比较低；

2013开源了新的分布式查询引擎：Presto。

后Presto分家：PrestoDB、PrestoSQL；PrestoSQL后被迫改名为Trino。

Presto为了应对快速、实时的查询聚合操作；支持多种数据源：关系数据库(mysql、oracle、DB2、SQLserver)、Hive、kafka等文件存储；支持各种文件格式；标准的SQL语法。

## 综合对比(重要)

![image-20210530120449941](DWS-Presto.assets/image-20210530120449941.png)

### 多表Join

Presto、Impala以及HAWQ在多表查询方面更有优势。

虽说Presto和Impala在多表查询方面的性能差别不大，但是Impala的功能有一些局限性，Impala不支持的功能是没有办法参与性能对比测试的，例如：不支持update、delete操作，不支持grouping sets语法，不支持Date数据类型，不支持ORC文件格式等等，而Presto则基本没有这些局限问题。

### 单大表聚合

在单表测试方面ClickHouse性能最好，其次是Presto，相比于HAWQ和impala以及SparkSQL在单大表聚合操作方面的表现也相对优秀。

### 简单

Presto是一个符合ANSI SQL规范的查询引擎，可以和各种BI工具配合使用：PowerBI、FineBI、Superset等。

### 兼容

Presto不仅支持Hive，还支持mysql、oracle等关系型数据库，也支持kafka、MongoDB、redis等非关系型数据库，对于实时数据库ClickHouse也能够完美支持。

Presto能够跨库读写，在这些不同的数据库中进行跨库关联查询，而无需进行复杂、缓慢且容易出错的数据复制过程；也可以将mysql库中的表数据直接读取插入到hive中。



## 使用场景（重要）

Presto： 资源充足、或数据量不大；多表查询性能优异，单标查询性能也不弱。并且有非常好的兼容性。

Hive：海量数据、或资源有限；稳定性好；被广泛兼容。

## 时间类型

日期类型：date '2021-11-11'

时间类型：timestamp '2021-11-11 00:00:00 000'



字符串转时间：date_parse(字符, 格式)

时间转字符串：date_format(时间, 格式)

```sql
#字符串转时间
with t as (
	select 
		timestamp '2021-05-30 17:35:30' as ts, '2021-05-30 17:35:30' as str
)
select ts = date_parse(str, '%Y-%m-%d %H:%i:%s') from t;

#时间转字符串
with t as (
	select 
		timestamp '2021-05-30 17:35:30' as ts, '2021-05-30 17:35:30' as str
)
select date_format(ts, '%Y-%m-%d %H:%i:%s') = str from t;
```



时间加减：date_add('单位',  数值,  原始时间)——》原始时间+值 后的	时间

时间差：date_diff('单位',  时间1,  时间2)    ——》时间2-时间1  后的	数值

```sql
#date_add
with t as (
	select 
		timestamp '2021-05-30 17:35:30' as ts, '2021-05-30 17:35:30' as str
)
select date_add('month', -1, ts) from t;

#date_diff
with t as (
	select 
		timestamp '2021-05-30 10:35:30' as ts, '2021-05-30 23:35:30' as str
)
select date_diff('day', date_parse(str, '%Y-%m-%d %H:%i:%s'), ts) from t;
```



## Presto优化（重要）

### 数据存储

1、ORC支持好

2、分区

3、SNAPPY

4、插入时排序



### SQL优化

1、select 需要的字段，不要select *

2、where 加分区条件

3、group by 高基数维度在前, 低基数维度在后

4、join时，大表放前面，小表放后面

5、order by加limit;

6、多个like，用regexp_like替代：regexp_like('字段名', '值1|值2|值3')



### 内存调优

#### User&System memory

user memory：用户底层的数据，查询时获取到的数据。

system memory：系统计算时，产生的变量消耗的内存。



#### 内存池

General_Pool、Reserved_Pool

平时用的是General_Pool，当General_Pool满时，会挑选占用内存最大的query到Reserved_Pool，以保证新的查询进入执行。

### 按城市、商圈、店铺分组统计

![image-20210602105327710](DWS-Presto.assets/image-20210602105327710.png)

1、按照cn取值，统计的结果没问题；

2、判断时，==先判断最细粒度的条件==，再判断宽粒度的条件；

3、可以再加上对应的rn，以便于理解：

​		row_number() over(partition by s.city_id, o.order_id) city_rn,
​		row_number() over(partition by s.trade_area_id, o.order_id) trade_area_rn,
​		row_number() over(partition by o.store_id, o.order_id) store_rn,

```sql
-- insert into yp_dws.dws_sale_daycount
with order_base as
(
	select 
-- 		维度
		SUBSTRING(o.create_date,1,10) as dt,
		province_id, province_name,
		s.city_id,
		s.city_name,
		s.trade_area_id,
		s.trade_area_name,
		s.id as store_id,
		s.store_name,
-- 		订单量指标
		o.order_id,
-- 		金额指标
		o.order_amount,
		o.plat_fee,
		o.delivery_fee,
-- 		判断条件
		o.order_from,
		o.evaluation_id,
		o.geval_scores,
		o.delievery_id,
		o.refund_id,
		row_number() over(partition by o.order_id) rn
	from yp_dwb.dwb_order_detail o
		left join yp_dwb.dwb_shop_detail s on o.store_id=s.id
		left join yp_dwb.dwb_goods_detail g on o.goods_id=g.id
	where o.is_pay=1
-- 	and o.order_id='dd190404391438bed2'
)
select 
-- 	=============维度=============
	dt
	,city_id
	,city_name
	,trade_area_id
	,trade_area_name
	,store_id
	,store_name
	,case 
		when grouping(store_id)=0
		then 'store'
		when grouping(trade_area_id)=0
		then 'trade_area'
		when grouping(city_id)=0
		then 'city'
		when grouping(dt)=0
		then 'all'
	end
	as group_type
-- 	=============金额=============
--   销售收入
	,sum(coalesce(order_amount, 0)) sale_amt
--   平台收入
	,sum(coalesce(plat_fee,0)) plat_amt
--   配送成交额
	,sum(coalesce(delivery_fee,0)) deliver_sale_amt
--   小程序成交额
	,sum(if(order_from='miniapp', coalesce(order_amount, 0), 0)) mini_app_sale_amt
-- 	安卓APP成交额
	,sum(if(order_from='android', coalesce(order_amount, 0), 0)) android_sale_amt
--  苹果APP成交额
	,sum(if(order_from='ios', coalesce(order_amount, 0), 0)) ios_sale_amt
-- 	PC商城成交额
	,sum(if(order_from='pcweb', coalesce(order_amount, 0), 0)) pcweb_sale_amt
-- 	=============订单量=============
-- 	单量
	,count(order_id) order_cnt
-- 	参评单量
	,count(if(evaluation_id is not null, order_id, null)) eva_order_cnt
-- 	差评单量
	,count(if(evaluation_id is not null and geval_scores<=6, order_id, null)) bad_eva_order_cnt
-- 	配送单量
	,count(if(delievery_id is not null, order_id, null)) deliver_order_cnt
-- 	退款单量
	,count(if(refund_id is not null, order_id, null)) refund_order_cnt
-- 	小程序单量
	,count(if(order_from='miniapp', order_id, null)) miniapp_order_cnt
-- 	安卓APP订单量
	,count(if(order_from='android', order_id, null))android_order_cnt
-- 	苹果APP订单量
	,count(if(order_from='ios', order_id, null))ios_order_cnt
-- 	PC商城单量
	,count(if(order_from='pcweb', order_id, null))pcweb_order_cnt
from order_base b
where b.rn=1
group by
grouping sets(
	dt,
	(dt, city_id, city_name, province_id, province_name),
	(dt, trade_area_id, trade_area_name, city_id, city_name, province_id, province_name),
	(dt, store_id, store_name, trade_area_id, trade_area_name, city_id, city_name, province_id, province_name)
)
-- order by dt desc,  sum(coalesce(order_amount, 0)) desc
;
```



### 按照品牌-统计（重要）

品牌与订单的关系，与商圈和城市的1对多不同，是==▁▁▁==的关系。

![销售DWS](DWS-Presto.assets/销售DWS-品牌-销售额.png)

1、品牌的销售额，累加的不是订单的金额，==而是▁▁▁的金额==；因为一个订单下可能有多个品牌的商品；

2、row_number() over(partition by o.order_id, ▁▁▁, ▁▁▁) 	brand_goods_rn；

3、按照不同分组统计时，分别多个不同的rn条件，rn从▁▁▁条件中移除，换到select的▁▁▁条件中；

判断：

```sql
case 
	when grouping(brand_id, store_id)=0
	then sum(if(brand_goods_rn=1, coalesce(goods_price, 0), 0))
	when grouping(store_id)=0
	then sum(if(store_rn=1, coalesce(order_amount, 0), 0))
	when grouping(trade_area_id)=0
	then sum(if(trade_area_rn=1, coalesce(order_amount, 0), 0))
	when grouping(city_id)=0
	then sum(if(city_rn=1, coalesce(order_amount, 0), 0))
	when grouping(dt)=0
	then sum(if(rn=1, coalesce(order_amount, 0), 0))
end
as sale_amt
```



实现：

1、查询出品牌字段；

2、按照新的品牌商品RN，去重后sum出金额；

3、按照新的RN，count+distinct出订单量；

4、==where限制是全局的，if限制是单行单列的==，由于出现多个RN=1条件，where转移到select的if中；

5、==grouping_sets合并SQL==，针对的是groupby语句，同时数据来源必须一致才能合并在一起。
